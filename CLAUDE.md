# Project Instructions — Workout (2-year strength tracker)

## 1. What this is

A personal strength-training tracker built around **one specific 2-year
program**, not a generic fitness app. Starting point: empty bar on squat/
bench/deadlift/OHP, 3 pull-ups, 15 push-ups. Two-year targets: squat 155 kg,
bench 130 kg, deadlift 210 kg, overhead press 80 kg, 20 pull-ups.

Single-page PWA, installable to a phone home screen, works offline.

## 2. Tech stack

- **One file:** `index.html` — all HTML/CSS/JS inline, no framework, no
  build step, no dependencies except Google Fonts (Barlow Condensed, IBM
  Plex Mono/Sans).
- `manifest.webmanifest` + `sw.js` (service worker) for PWA install +
  offline. Icons generated by `scripts/gen_icons.py` (no external assets).
- **Storage:** `localStorage`, with `window.storage` tried first as a
  legacy fallback (harmless remnant, not something this app relies on —
  a plain browser always falls through to `localStorage`).
- **Deploy:** GitHub Pages serving from `main`. There is no staging
  branch or review process — work happens on a short-lived feature
  branch, then a fast-forward merge straight to `main`, because that's
  literally what makes it go live. Don't leave finished work sitting on
  an unmerged branch (bit the project once already — see decision log).

## 3. Current status

Four tabs: **Train** (today's session — sets, weight, rest timer, deload
logic) · **History** · **Body** (attribute tracking + PR sheet) · **Cardio**
(independent activity log).

- `state.blocks[]` holds the training program as a sequence of blocks.
  **Block 01** is hand-authored with its own fixed Reset → Load-in →
  Pyramid phase schedule (`phaseSchedule:true`), unchanged since it was
  already mid-run with real logged data when the multi-block system was
  built. **Block 02 onward** are auto-generated: each of the four lifts
  independently runs one of three progression modes —
  **linear** (every clean session adds weight) → **weekly** (weight held
  a full week, advances only if the whole week was clean) →
  **block** (periodized volume/intensity/deload wave, first-cut, unproven
  — see open items).
- When a block ends, the app proposes the next one: escalates a lift's
  mode (never downgrades) if it stalled — 2+ deloads or <5% e1RM growth
  — with a ~7% weight back-off on any mode change. User confirms/adjusts
  dates before it commits.
- **Block goal** panel: projected end-of-block weight per lift, assuming
  every remaining scheduled session/week goes clean. Explicitly labelled
  "not a promise."
- **Two-year targets** panel: per-lift progress bar toward the fixed
  targets, plus one shared **time-elapsed bar** (Block 01's start date to
  +2 years, clamped at 100%) so you can eyeball pace at a glance.
- **Body tab:** a simple SVG figure with four color-coded points (pulse,
  weight, biceps, waist) matching four attribute cards. Each logs a
  *dated* value — full history per attribute, not just a current number
  — specifically so trend over 2 years is visible. Below that, a records
  grid surfaces existing PRs (`state.best`/`state.bwBest`) plus best
  cardio pace — display only, no new tracking there. Replaced a static
  "Baseline" footer line that had no function.
- **Cardio tab:** independent log (date, type, distance, time, note).
  **Deliberately not wired into the lift progression/mode system** —
  running/cycling/rowing/swimming don't have the same progressive-
  overload shape as a barbell lift. Best pace is distance/time-normalized
  (min/km) so different distances compare fairly.

## 4. Decision log

- **PWA made real, not cosmetic.** `TODAY` was hardcoded to one date —
  fixed to read the device clock. Added manifest + generated icons +
  service worker for actual installability. The service worker
  deliberately does **not** auto-swap on a new deploy (`skipWaiting()`
  removed from `install`) — it stays in "waiting" and the page shows an
  update banner; only a user tap activates it. Rationale: a silent swap
  mid-workout could replace app logic under an in-progress session.
- **Real dates, not hand-computed month constants.** The old calendar
  used `AUG_START=5, SEP_START=1` — a manually-worked-out weekday offset
  per month. Replaced with actual `Date`/ISO strings throughout
  (`sessions` keyed `YYYY-MM-DD`, not `m-d`), because a 2-year program
  cannot run on hand-computed constants for every month it touches.
- **Migration, not a breaking change.** Old saves under `block01v3` are
  migrated in place into the new `workout-v1` shape on first load. The
  old key is left untouched as a safety net — never deleted.
- **Cardio stays a simple log, no periodization, until asked for.**
  Explicit user call: "we can build a training-block structure for
  cardio later if I decide to take it more seriously." Not built now,
  not stubbed — just noted here so it isn't forgotten.
- **Block mode (periodized volume/intensity/deload) is an honest
  first-cut.** Nobody will reach it for months (only kicks in after both
  linear and weekly have stalled on a lift), so it hasn't been validated
  against real training data. Worth revisiting with real numbers once
  someone's actually approaching it, not tuned further on guesses now.

## 5. Open / deferred

- Cardio periodization — deferred by user request, see decision log.
- Block-mode's exact wave shape (4 volume / 3 intensity / 1 deload weeks,
  ~7% back-off on stall) is unvalidated — first real usage should be
  treated as a signal to revisit, not as confirmation it's right.
- No custom app icon art beyond the generated barbell-mark placeholder.

## 6. How to start a session

Check section 3 for what's built and section 5 for what's explicitly
deferred before assuming something is missing by accident. Section 4
records *why*, not just *what* — don't silently overturn a decision
there; if it needs to change, say so explicitly, same as the log itself
was built to do.
